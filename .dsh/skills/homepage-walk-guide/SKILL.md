# homepage-walk 完全指南

一条街，走着看完你写过的所有东西。

| | |
|---|---|
| 配套操作手册 | `homepage-walk` skill（改现有项目、发布流程、踩坑清单） |
| 参考实现 | `/Users/goodyhao/toy/homepage-walk/` |
| 抓项目脚本 | `scripts/fetch_projects.py`（本 skill 目录下） |
| 耗时 | 抓 + 筛 30 分钟，写文案 1 小时，调画面看心情 |

## 0 先看懂这张图（视觉语言）

画面上每个元素都在说话，先弄明白它们各自代表什么，才知道该改哪个：

| 元素 | 代表 | 由什么决定 |
|---|---|---|
| 一间房 | 一个项目 | 配置里一个站台 |
| **房高** | 项目的成绩 | `30 + √stars × 5`；`upstream` 的改按 commits 算 |
| **房色** | 主语言 | `palette` 里的语言色（GitHub linguist 配色） |
| **窗户（屏幕）** | 项目长什么样 | 真实截图，或自绘徽章 |
| 屋顶小旗 | 这个项目有 star | `stars >= 2` 且不是 upstream |
| 屋顶紫红箭头 | 这是给**别人**项目做的贡献 | `upstream: true` |
| 门口石牌 | 年份 | `year` |
| 地上的街 + 刻度轨 | 时间轴 | 站台顺序 + 年份 |
| **天色** | 走过的进度 | 与项目的真实日期无关，是"旅程感" |
| 走的小人 | 你自己 | 固定，不用配 |
| HUD 两行 | 当前正在经过的项目 | 名字 / 年份·语言·成绩 / 一句备注 |

**关键设计**：小人在画面里走，世界在脚下滚。所以世界比画面宽得多，房子是一间间路过的。

## 1 六步总览

```
① 抓项目   gh repo list → scripts/fetch_projects.py → projects.json 骨架
② 筛选     私有必丢；fork/归档默认丢；练习玩具人工判断；同类合并
③ 配风格   选天色、挑徽章、定房高规则
④ 写文案   每条中文备注 ≤ 274 像素
⑤ 出片     render.py → 960×342 循环 GIF
⑥ 上主页   丢进 profile 仓库，README 引用
```

## 2 第一步：自动抓下所有项目

```bash
cd <你的 homepage-walk 项目>
python3 <本skill目录>/scripts/fetch_projects.py <你的GitHub用户名> > projects.json
```

先决条件：装了 `gh` 并且已登录（`gh auth status` 能过）。

**脚本干这些事**：

- `gh repo list` 拉全部仓库（默认上限 300）
- 按规则**过滤**（下一节），丢弃的每一条都在 stderr 里给出理由
- 每站填好 `name` / `repos` / `year` / `lang` / `stars`
- **猜徽章**：看名字形状 → 看名字里有没有徽章名 → 看描述关键词，三轮下来约 85% 准
- **猜合并**：把 `xxx-java-8` / `xxx-java-17` / `xxx-frontend` 这类后缀剥掉分组，
  同组的提示"可能是同一个项目"
- 标出"练习/玩具/0 star"，提醒你人工再看一遍
- `zh` 字段：中文描述直接截断到 274 像素；英文描述**不硬截**，留中文占位等你写

**stdout 是干净的 JSON，报告全走 stderr**，所以可以直接重定向到文件。

输出里带一份 `_todo` 五条，就是下面第 3、4 步要做的事。

## 3 第二步：筛选 —— 哪些上街，哪些必须过滤

这是最需要判断力的一步。分四档：

### 必须丢（脚本强制）

| 情况 | 为什么 |
|---|---|
| **私有仓库** | **渲染成图 = 公开它的名字和描述。** 这一条没有例外 |
| 空仓库 | 没东西可说 |

### 默认丢（有开关）

| 情况 | 默认 | 想要的话 |
|---|---|---|
| fork | 丢 | 大多数 fork 是纯搬运，上街等于往自己脸上贴别人做的项目。**但如果本人真的在那边提交过**，那是有价值的——用 `upstream: true` 单独标出来 |
| 已归档 | 丢 | `--keep-archived`。也可以留着（有故事），但适合让它"关灯" |
| star 低于 N | 不丢 | `--min-stars N` |

**判断一个 fork 值不值得上街**：

```bash
gh api "repos/<owner>/<repo>/commits?author=<owner>&per_page=1" --jq 'length'
# 返回 1 = 你在这个仓库有提交，值得考虑；返回 0 = 纯搬运，丢掉
```

### 要人工判断（脚本只提示）

- **练习/作业/玩具**：`homework` `lab` `study` `demo` `practice` 这类名字。**不一定要删**——
  如果它是你时间线的起点（"第一次动手做 XX"），留着反而有叙事价值。参考实现里
  `saasi-experiment`（本科课程实验）和 `practice1`（和朋友写的第一个东西）都留着了。
- **0 star**：不是缺点。你自己的项目本来就没几个人 star，全删就只剩别人的 fork 了。
- **名字特别长的**：HUD 第一行会被截断（拉丁字体 11px，`fit()` 兜底加 `..`）。
  超过约 30 个字符考虑在配置里改短一点（`name` 和 `repos` 是分开的，可以起短名）。

### 合并同类

几个仓库其实是一个项目时，塞进**同一个站台的 `repos` 数组**，街上只占一栋房：

```jsonc
{ "name": "basic-check", "repos": ["basic-check-java-8", "basic-check-java-17"], ... }
```

脚本会猜（按后缀分组），但**同义不同名它认不出来**——参考实现里
`gomoku-frontend` 和 `gumuku-backend` 是同一个五子棋（注意 backend 拼错了），
机器分不出，靠人眼。合并的线索：同一时期创建、描述互相提到、一个前端一个后端。

### 共上街多少个？

**先记住这条（实测出来的，反直觉）**：

> **体积跟站台数没关系，只跟「画布大小 × 帧数」有关系。**
> 30 站在 180 帧下是 2.19 MiB，14 站在同样 180 帧下是 1.97 MiB —— 差不多。
> （严格说画面内容也影响压缩：把 3 张复杂截图换成徽章后，体积又掉了 0.18 MiB。）

站台数决定的是**每站停留多久**。要维持"每站约 1 秒"（低于 0.8 秒就看不清 HUD 上的字），
就得 `帧数 ≈ 站台数 × 12`，**加帧数才会加体积**：

| 站台数 | 帧数（维持 1 秒/站） | 时长 | 体积 |
|---|---|---|---|
| 10–14 | 120–170 | 10–14 秒 | ~1.5–2.1 MiB ✅ |
| 18–22 | 220–265 | 18–22 秒 | ~2.9–3.4 MiB |
| 30 | 360 | 30 秒 | ~4 MiB ⚠️ |
| 30（偷懒不补帧） | 180 | 14–15 秒 | 2.2 MiB，但**每站只停 0.5 秒，名字一闪而过** |

所以"站台多"的真实代价是**片子变长**，不是文件变大。30 站的循环放在主页首屏，
观众看两秒就走了，等于白做。

**建议 12–16 站**：按时间跨度挑有代表性的，让每一站都有理由存在。
参考实现从 32 站砍到 14 站，时长从 23 秒收敛到 14.4 秒，每站停够 1 秒。

## 4 第三步：怎么画 —— 世界的构造

**世界在 320×114 的低分辨率里画，最后整体最近邻放大 3 倍成 960×342。**
所有坐标按世界像素想。

### 绘制层次（从后往前）

| 层 | 内容 | 视差 |
|---|---|---|
| 1 天空 | 整帧一个时刻的颜色，只做竖直渐变 | — |
| 2 星星 / 云 | 夜晚星星、飘云 | 0.18 / 0.22 |
| 3 远山 | 三条正弦叠加的山脊线 | **0.28** |
| 4 中景楼群 | 随机高度的剪影 + 零星窗灯 | **0.55** |
| 5 地面 | 地表亮线 + 土色 + 碎石 | 1.0 |
| 6 房子 | 房子 + 屏幕 + 旗 + 门 + 年份石牌 | 1.0 |
| 7 小人 | 影子 + 4 帧走路循环 | 1.0 |
| 8 HUD | 刻度轨 + 两行文字 | 固定 |

视差是"横向移动有速度感"的全部来源，别删。

### 一间房的解剖

```
        ┌─ 旗（stars>=2）         ┌─ 合并箭头（upstream）
   ┌────┴─────────────┐
   │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │ ← 屋檐（语言色提亮）
   │ ┌──────────────┐ │
   │ │   屏  幕     │ │ ← 40×24 世界像素：真截图 或 徽章
   │ └──────────────┘ │
   │       ┌──┐       │ ← 门
   │       └──┘       │
   └──────────────────┘
         [ 2025 ]         ← 年份石牌
   ══════════════════════  ← 地平线
```

房宽 48、站距 60——**站台变多就压这两个**，压到 40/52 还能看，再小屏幕就糊了。

### 屏幕上的两种内容

| | 真实截图 | 自绘徽章 |
|---|---|---|
| 是什么 | 项目自己的截图 | 代码画的 20×16 图案 |
| 什么时候用 | 有**干净、明亮、细节铺满**的截图 | 其余全部情况 |
| 怎么配 | `"shot": "文件名.png"` + 图放 `assets/screens/` | `"emblem": "chart"` |

**像素化会把烂图变得更烂。** 深色 IDE 截图、单色 logo、sprite sheet、竖版手机截图，
进了 40×24 的网格就是一坨糊的。宁可画徽章——徽章至少形状清楚。

挑截图的判据（经验值）：细节要铺满全画面、不要大片纯色、饱和度别太高、别太黑也别过曝。
参考实现 30 个仓库里只有 3 张图过关，这是正常的，不是你没找对。

### 文字怎么变成像素字

不能直接用抗锯齿字体（一放大就糊）。做法是：**用真字体渲染 → 按阈值二值化 → 得到像素字**。

| 语言 | 字体 | 字号 |
|---|---|---|
| 拉丁 | Menlo | **10–11px**（9px 会烂） |
| 中文 | Hiragino Sans GB | **12px**（11px 发虚） |

两个坑：**PIL 默认字体没有中文**；macOS 上**没有 PingFang.ttc**（常见教程会让你用，实际找不到）。

## 5 第四步：风格 —— 有哪些，怎么分

风格分**五条轴**，互相独立，可以分别调。

### 轴 1：时间（最显眼的风格）

天空有 **8 个色阶**，从小人走过的进度插值（**不是**按项目真实年份——2026 年有 9 个项目，
按年份的话天会一直卡在同一个颜色）：

```
天没亮 → 破晓 → 清晨 → 上午 → 正午 → 午后 → 黄昏 → 入夜
```

每段是 `(天顶色, 中景色, 地平线色)` 三个 RGB。**这是整张图情绪的主要来源**，
换一套 `SKY` 数组就是换一种基调。想固定成单一时刻，把 8 组写成一样的即可。

### 轴 2：房子的类型

| 类型 | 触发条件 | 视觉差异 |
|---|---|---|
| 自有项目（默认） | — | 常规房子 |
| **有成绩** | `stars >= 2` | 屋顶插小旗 |
| **上游贡献** | `upstream: true` | 屋顶紫红合并箭头，房高按 commits 算，抑制旗子 |

### 轴 3：屏幕内容

真截图 / 自绘徽章，见上一节。**混合是正常的，而且好看**——因为所有屏幕最后都过同一张
全局调色板做像素化，图源再杂也会被统一成同一个世界。

### 轴 4：徽章语义（28 种，分 5 类）★

这是最实用的一节：**新项目该配哪个徽章，按"这个项目是干什么的"查表**。

| 类 | 什么时候用 | 图案 |
|---|---|---|
| **界面与产品** | 给用户直接用的东西 | `window` 应用窗口 · `page` 网页/文档 · `phone` 移动端 · `cards` 卡片/信息流 · `clipboard` 表单/任务 · `prompt` 命令行/技能 · `avatar` 人/主页 |
| **数据与图表** | 处理数据、给结论 | `chart` K线/行情 · `bars` 柱状图/统计 · `graph` 折线/网络图 · `pulse` 波形/信号 |
| **工程与架构** | 系统、服务、基础设施 | `microservice` 微服务 · `nodes` 多智能体/编排 · `chip` 嵌入式/硬件 · `db` 数据库 · `gear` 框架/引擎 · `plug` 插件/MCP · `merge` 上游合并 |
| **工具与物件** | 具体的家伙什 | `toolbox` 工具箱 · `book` 书/词典/学习 · `potion` mod/补丁 · `shield` 校验/权限 · `sparkle` 推荐/策展 |
| **游戏与趣味** | 玩的东西 | `board` 棋盘/游戏 · `tictactoe` 井字棋 · `play` 播放器 · `mask` 桌游/推理 · `robot` 机器人/AI |

**兜底是 `window`**（应用窗口外壳）——它是唯一一个"什么项目都不算太违和"的图案。

加新图案：在 `render.py` 的 `emblem()` 里加一个 `elif kind == "xxx":` 分支，
用 `Px` 的 `rect / frame / line / disc / set` 在 **20×16** 画布上画。
可用颜色：`col`（语言色）、`hi`、`lo`、`deep`、`white`、`warm`。每个图案平均 7 行代码。

**别搞太复杂**：20×16 就 320 个像素，细节一多就糊。看现有图案的复杂度——最复杂的
`cards` 和 `merge` 也就 14 行，`pulse` 只有 3 行却最容易认。

### 轴 5：语言配色

房子颜色 = 主语言色，取自 `palette`（GitHub linguist 配色）。
如果某几个项目的语言色太像（比如 Java 的橙和 Rust 的沙色），房子会撞色——
可以把其中一个的 `lang` 改成更醒目的语言，或者手动调 `palette` 里的值。

### 想整体换风格？

- **换基调** → 改 `SKY`（8 组三色）
- **换房子疏密** → 改 `HOUSE_W` / `PITCH` / `MARGIN`
- **换整体色数** → `--colors`（但**实测对体积几乎没影响**，别指望它压体积）
- **换地面/远景色** → `GROUND_TOP` / `GROUND_MID` / `GROUND_LOW`

## 6 第五步：出片

```bash
PY=/Users/goodyhao/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/bin/python3

$PY render.py --preview 0.45        # 先拍静帧看画面（秒出），改画面一律用这个
$PY render.py --frames 180 --fps 12 --scale 3    # 出正片
$PY render.py --poster 0.52 --scale 4 --title    # 出封面
```

**体积主要由画布大小和帧数决定**（画面内容越花也越大）。

| 配置 | 体积 |
|---|---|
| `--scale 3` (960×342) `--frames 180` | 1.97 MiB ← 推荐 |
| `--scale 3 --frames 240` | 2.6 MiB |
| `--scale 2` (640×228) `--frames 180` | 1.2 MiB ⚠️ 见下 |

**宽度只能选 960**：GitHub 正文栏约 880px，README 里用 `width="100%"` 时，
640 会被浏览器**拉伸**到 880 变糊，960 只是轻微缩小。

两个白费劲的方向（都实测过）：**调调色板**（32/44/72 色体积一模一样）、
**帧间差分**（Pillow 的 GIF 编码器不认逐像素透明，做了等于没做）。

## 7 第六步：放到主页

### 放哪：两种都行

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 图放主页仓库** | `images/pixelwalk/pixelwalk.gif` + README 相对路径 | 简单，一个仓库自洽。缺点是主页仓库要存 2 MB 二进制 |
| **B. 图放独立仓库** | 图放 `homepage-walk` 仓库，主页 README 用绝对 URL | 主页仓库干净。URL 形如 `https://raw.githubusercontent.com/<owner>/homepage-walk/main/out/pixelwalk.gif` |

参考实现用的是 A。

### README 里怎么写

```html
<p align="center">
  <img src="images/pixelwalk/pixelwalk.gif" width="100%"
       alt="A pixel character walks past every project I have shipped, 2018 to 2026">
</p>
<p align="center">
  <sub><b>Pixel Walk</b> · 2018 → 2026，14 个项目排成一条街。<br>
  数据取自 GitHub API，画面由代码逐像素绘制。</sub>
</p>
```

`width="100%"` 撑满正文栏；`alt` 别省，手机和读屏要靠它。

### ⚠️ 提交身份（最容易出事的地方）

**如果你的 git 全局身份用的是想保密的邮箱，绝对不要用它提交到公开仓库。**
参考实现那边的本地身份是一个专门从历史里脱敏掉的 QQ 邮箱，所以每次提交都显式覆盖：

```bash
git -c user.name="你的名字" \
    -c user.email="<你的GitHub数字ID>+<用户名>@users.noreply.github.com" \
    commit -m "Update Pixel Walk"
```

用 `-c` 而不是 `git config`——后者会持久化，污染你所有仓库的配置。
GitHub 数字 ID 在 `https://api.github.com/users/<用户名>` 的 `id` 字段。

### 推完验收

```bash
# 1. 提交作者对不对
gh api repos/<owner>/<owner>/commits --jq '.[0] | "\(.sha[0:7])  \(.commit.author.name)  \(.commit.message|split("\n")[0])"'
# 2. 图能不能访问
curl -sIL -o /dev/null -w "%{http_code}\n" https://raw.githubusercontent.com/<owner>/<owner>/main/images/pixelwalk/pixelwalk.gif
# 3. 主页真的引用了
curl -sL "https://github.com/<owner>" | grep -oE 'src="[^"]*pixelwalk[^"]*"'
```

## 8 自检清单

- [ ] 没有私有仓库上街（**这条最要紧**）
- [ ] fork 只留本人真有提交的，并且标了 `upstream`
- [ ] 同类仓库合并成一站了
- [ ] 站台数在 12–20 之间；时长在 12–20 秒之间
- [ ] 每条 `zh` 都量过宽度，没有 `..` 截断
- [ ] 每站的 `emblem` 跟项目性质对得上（查轴 4 那张表）
- [ ] 截图都裁成 5:3 了，没有深色糊图
- [ ] 拍过 `--preview` 的三个时刻（破晓 / 白天 / 入夜），画面没问题
- [ ] 抽帧拼 filmstrip 看过整段
- [ ] 体积 ≤ 2.5 MiB
- [ ] 提交身份不是想保密的那个邮箱

## 9 常见问题

**Q：能不能每天自动更新？**
先问"每天真的变了什么"。参考实现那个账号 30 个仓库里 26 个三个月没动过，
日更只会天天产出同一张图。要做就做**事件驱动**：daily cron + 有变化才提交
（新仓库 → 多一栋房；star 破关口 → 加盖；归档 → 关灯）。

**Q：能不能输出 SVG 而不是 GIF？**
能，而且更好：SMIL 动画 SVG 大约 50–80 KB、任意缩放都清晰、GitHub 的 camo 代理直接播。
但要重写渲染层（静态世界一个 `<g>`、镜头一个 `animateTransform`、小人一个
`animateTransform` + 4 帧 `<set>`、屏幕素材 base64 内嵌）。这是最值得做的下一步。

**Q：能不能自动抓项目的截图？**
试过，删了。30 个仓库只有 3 张图过质量线，为这 3 张养 330 行抓取+打分代码不划算；
而且打分器会把大红图标和 sprite sheet 排第一，最后还是人工纠。
**手工放图 15 分钟，结果更好。**

**Q：小人能换吗？**
能。`WALK_FRAMES` 是 4 组 10×17 的字符网格，用 `.hsbcpeo` 这些字符当色号画，
改字符画就行。记得保留深色描边（`draw_walker` 里那段），没有描边小人会糊进背景。

**Q：只有三五个项目怎么办？**
照样做。站距调大（`PITCH` 80–100），房子间距拉开，每站停久一点，
帧数降到 90–120。**短而清楚的片子比长而拥挤的好。**
